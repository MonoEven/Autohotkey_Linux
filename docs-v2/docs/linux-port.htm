AutoHotkey v2 Linux Port

This documentation set accompanies the AutoHotkey v2.0.26 Linux port (MonoEven/Autohotkey_Linux). The pages in this site are the official AutoHotkey v2 documentation, adapted for the Linux port. Only AutoHotkey v2 syntax is supported; the AutoHotkey v1 language, the v1-to-v2 migration material, and all Windows-specific behavior are not part of this port.

Language and syntax

  • v2 only. The interpreter is built from the AutoHotkey v2.0.26 source. v1 syntax, commands and directives are not supported.
  • See Scripting language, Concepts and conventions, and the list of built-in functions for the supported v2 feature set.

Examples in this documentation

These pages mirror the official AutoHotkey v2 documentation, so their examples fall into three groups on Linux:

  • Run as-is. Pure-language examples (variables, loops, strings, math, files, objects, RegEx, ...) run unchanged. Windows-style paths like C:\... are treated as plain (oddly named) files on Linux; use Linux paths (/tmp/..., A_Desktop, ~) in your own scripts.
  • Platform-adapted. Pages for DllCall and the COM functions (ComObject, ComObjGet, ...) add a Linux example block at the top of their Examples section that uses native .so libraries or the D-Bus bus; the original Windows examples are kept for reference only.
  • Not available on Linux. Examples using Windows-only features (tray icon via TrayTip/TraySetIcon, SafeArray creation via ComObjArray, SendMessage/ PostMessage/OnMessage, the Windows registry, ...) are kept for reference; calling those functions raises a clear error. Many examples elsewhere are also short snippets that depend on context (a preceding variable, a hotkey label, a window with a specific title); they illustrate syntax rather than being standalone programs.

What works on Linux

All 367 built-in functions listed in the worklist are implemented (3 not-implemented error paths: ComObjArray, TrayTip, TraySetIcon); 1063 doc-check assertions pass under Xvfb (including 29 for DllCall against native .so libraries and 18 for the D-Bus COM layer). The port has two display backends:

  • X11 backend (preferred when DISPLAY is set, including XWayland sessions): window management (Win*), controls, hotkeys via XGrabKey/XGrabButton (keyboard and mouse-button/wheel hotkeys), pixel/monitor access, dialogs, ToolTip, ImageSearch and window shapes.
  • Native Wayland backend (used when no X display is available): xdg-shell windows, virtual keyboard/pointer input (zwp_virtual_keyboard_v1 / zwlr_virtual_pointer_manager_v1), screen capture via wlr-screencopy. Global hotkeys in Wayland sessions go through the unified input backend (input_backend.h), which selects automatically:
    • GNOME Shell extension backend (GNOME 49, zero-confirmation exclusive hotkeys: 1::/^1::/F12:: grab and suppress the physical key with no per-binding dialog). The companion extension (extension/ in the repo) is a thin D-Bus broker (io.github.autohotkey.GlobalHotkeys1) that registers accelerators through Meta.Display.grab_accelerator() + Main.wm.allowKeybinding() (the whitelist step the portal backend performs via shellDBus) and relays activations back; it never parses AHK, executes commands or forks. Verified on Ubuntu 25.10 + GNOME 49 (E2E: physical 1 fires the hotkey with no confirmation dialog, the key is suppressed from the focused app, exiting the script restores the key, kill -9 releases the grab fail-open, Ctrl+1/F12 and key-repeat work, and a gnome-shell extension reload (disable/enable) is followed by automatic re-registration). Protocol hardening (v2): activations are delivered directed to the registering owner only (no broadcast); hotkey ids are owner-scoped (<unique-bus-name>/<hotkey>); ClearOwner takes no owner argument (the caller's own unique name is used); registrations are batched (RegisterMany/UnregisterMany) with bounded timeouts, and only the Activated signal is consumed (Deactivated is explicitly ignored). Capability scope (v1): exclusive hotkeys only — ~1:: passthrough, remaps, a & b:: and full wildcards are NOT in this backend (evdev/ahk-inputd lane); 1 up:: has its signal source (accelerator-deactivated is relayed) but is not yet consumed by the runtime.
    • XDG Global Shortcuts Portal backend (org.freedesktop.portal.GlobalShortcuts, GNOME 45+/KDE, the standard safe fallback): Hotkey registrations bind with the compositor and fire on the physical key. Caveat: a few compositor/driver builds (e.g. Ubuntu 25.10 ’s xdg-desktop-portal 1.20.3 + GNOME 49) only accept binds when they can resolve a valid app identity for the caller (a bare CLI resolves none and is rejected); run from a matching .desktop/app scope on those systems.
  • Backend selection: AHK_INPUT_BACKEND=auto|x11|portal|gnome-shell|evdev (auto: X11 session → X11; GNOME Wayland with the extension installed → gnome-shell; other Wayland → portal; evdev reports “backend not installed” until ahk-inputd ships). AHK_FORCE_GLOBAL_SHORTCUTS=1 keeps its documented meaning: explicitly require the standard Portal backend (it is not reused for the GNOME Shell backend); only 1/true/yes/on count as true, and an unknown AHK_INPUT_BACKEND value prints a clear startup warning instead of silently running a different backend. An XWayland/Xorg session remains the stable fallback on all systems.
  • Unicode text input (round-34): SendText/Send and hotstring replacements now deliver non-ASCII characters instead of dropping them. On X11/XWayland every Unicode character is sent as a key event mapped to its keysym (a spare keycode is temporarily remapped when the layout has no binding for the character, exactly like xdotool); Chinese, Japanese, Korean, accented Latin, Emoji and combining marks all work. On a pure Wayland session non-ASCII runs use the controlled clipboard-paste fallback (set clipboard → Ctrl+V → restore) on compositors with the virtual-keyboard protocol (wlroots-based desktops such as sway); on compositors without it (e.g. GNOME) the send raises a clear error naming the character instead of silently dropping it.

Differences from Windows AutoHotkey

  • GUI windows are implemented over GTK3 (Gui/ GuiControl/Menu work on X11/XWayland and need a display; pure headless sessions raise a clear error).
  • COM is implemented over D-Bus: ComObject("service") (or ComObjGet) creates a proxy for a D-Bus service; method calls and property access map to D-Bus method/property calls; ComValue wraps typed values (integers, doubles, strings, booleans, bytes). Windows COM interfaces (IUnknown/IDispatch pointers, SafeArrays, events) do not exist on Linux; ComObjQuery/ComObjConnect/ComObjArray raise an error.
  • DllCall is supported for native Linux shared objects (.so): functions are resolved with dlopen/dlsym and called through libffi, with Int/Int64/Short/Char/Float/Double/Ptr/Str/AStr/WStr argument types, by-address (&Var) output parameters, and HRESULT-style error reporting. Windows DLLs are not loadable.
  • No registry access (Windows registry), no Win32 messages for other windows.
  • The SoundGet*/SoundSet* mixer functions are available via pactl (PipeWire/PulseAudio) with an ALSA amixer fallback; SoundPlay (paplay/aplay) and SoundBeep (terminal/X11 bell) work too. The tray icon (TrayTip) and compiled-script packaging are not available.
  • CoordMode/SendMode semantics are honored; hotkeys work through XGrabKey (keys) and XGrabButton (mouse buttons/wheels) on X11/XWayland, and through the GNOME Shell extension or the Global Shortcuts Portal on Wayland (see the "Native Wayland backend" section above). LoadPicture decodes BMP/ICO/PNG/GIF/CUR/JPEG/PPM.

See CHECK_REPORT.md for the complete per-module report.

Latest release

The project is in technology-preview status: the language coverage is broad and the X11/XWayland backend is usable for real automation, but native-Wayland global hotkeys, Unicode input on compositors without a virtual keyboard, and cross-app control automation remain young; treat new installs accordingly. The latest release is v2.0.26-linux.13. Highlights of this release:

  • Unicode text input: SendText/Send and hotstring replacements deliver non-ASCII characters on X11/XWayland (keysym transmission, xdotool-style spare-keycode remap) and via the clipboard-paste fallback on virtual-keyboard Wayland compositors; a clear error is raised where no injection path exists (see "What works" above).
  • GNOME Shell backend hardening: activations are directed to the registering owner, ids are owner-scoped, ClearOwner no longer accepts an owner argument, only Activated is consumed, registrations are batched with bounded timeouts, and the event queue is dynamic with overflow counting.
  • Configuration correctness: AHK_FORCE_GLOBAL_SHORTCUTS only treats 1/true/yes/on as true; unknown AHK_INPUT_BACKEND values print a clear startup warning.
  • Unified input backend (input_backend.h): AHK_INPUT_BACKEND=auto|x11|portal|gnome-shell|evdev auto-selection; AHK_FORCE_GLOBAL_SHORTCUTS=1 keeps its documented meaning (explicitly require the Portal backend).
  • GNOME Shell extension backend (GNOME 49 Wayland): zero- confirmation exclusive hotkeys (1::/^1::/ F12:: grab the physical key with no per-binding dialog), with automatic re-registration after a shell/extension reload and fail-open release on script exit or crash. See the "Native Wayland backend" section above.
  • Hotstrings are implemented (round-32): full capture-engine triggering with C/*/O/X options, case-follow, HotIf and end characters; InputHook key capture (round-33) and mouse hotkeys (round-30) are also in.
  • Doc-check: 1063/1063 assertions pass on both the normal and the ASan builds; regression 27/27, Wayland 15/15, XWayland 247/247.

Roadmap (P1/P2 of the check0819 review):

  • evdev/uinput broker (ahk-inputd) — the lane that would bring passthrough, remaps, key-up, custom combos and wildcards to native Wayland. Design notes: a small privileged daemon reads /dev/input/event* (evdev) for key events and injects through /dev/uinput; the permission model is input group membership or a polkit rule granting io.github.autohotkey.inputd read/inject; hotkey policy stays in the AHK runtime (the daemon only mirrors key events and injected output, the XRecord+XTEST analogue on X11). Not started yet; tracked in GOALS.md.
  • IME integration — Unicode hotstrings/InputHook already work at the keysym level (round-34); a full IME (ibus/fcitx) commit path needs the Wayland text-input protocol or the evdev lane.
  • AT-SPI control backend — real cross-app control automation for GTK/Qt/Electron via the accessibility tree; no implementation yet.
  • Desktop compatibility matrix — CI currently verifies Ubuntu 24.04 (Xvfb/sway/XWayland); Fedora, Debian, Arch and GNOME/KDE/older-GNOME runs are planned (see GOALS.md).

Related work and credits

This port is an independent implementation, but it builds on the ideas and feedback of the AutoHotkey-on-Linux community:

  • AHK_X11 — a from-scratch reimplementation of AutoHotkey v1 (2004-era syntax) in Crystal, X11-only (XRecord global key monitoring + XTEST injection), distributed as a single AppImage; the most widely used AutoHotkey-on-Linux project and a frequent reference for X11 key capture/injection behavior (see also its forum thread).
  • AutoHotkey v2 — the upstream Windows project this fork is based on; all language semantics come from it.

Build and install

git clone --branch linux-port https://github.com/MonoEven/Autohotkey_Linux.git
cd Autohotkey_Linux
cmake -S . -B build-core
cmake --build build-core -j$(nproc)
build-core/source/linux/core/ahk_core your-script.ahk

Prebuilt packages (tar.gz / .deb) and an installer are published with each GitHub Release: releases.
